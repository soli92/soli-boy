# TSK-051 — Workflow CD Vercel: cd-vercel.yml (US-042)

## Context

US-042 richiede il deploy automatico su Vercel preservando gli header COOP/COEP
già dichiarati in `packages/app/vercel.json`. Le decisioni di prodotto ratificate
chiudono il gap `vercel-deploy-trigger-policy`. [^src: management/kanban/EP-011-ci-cd/US-042-continuous-deployment-vercel/US-042.md §Business Rules]

**Decisioni di prodotto incorporate (ratificate dall'owner):**
- Deploy di PRODUZIONE su tag `v*` (release)
- Deploy di PREVIEW automatico sulle PR
- Output frontend: `dist` di `packages/app`
- `vercel.json` esistente in `packages/app/` con header COOP/COEP — non toccare
- Segreti GitHub necessari: `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`
  (creazione dei segreti = gate umano: non eseguita da questo TSK)

## Technical Specs

```yaml
# .github/workflows/cd-vercel.yml
name: CD — Vercel

on:
  push:
    tags:
      - "v*"
  pull_request:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: packages/app

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Node 20
        uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: "npm"
          cache-dependency-path: packages/app/package-lock.json

      - name: Install dependencies
        run: npm ci

      - name: Build
        run: npm run build

      - name: Deploy a Vercel (production su tag, preview su PR)
        uses: amondnet/vercel-action@v25
        with:
          vercel-token: ${{ secrets.VERCEL_TOKEN }}
          vercel-org-id: ${{ secrets.VERCEL_ORG_ID }}
          vercel-project-id: ${{ secrets.VERCEL_PROJECT_ID }}
          working-directory: packages/app
          vercel-args: ${{ startsWith(github.ref, 'refs/tags/v') && '--prod' || '' }}
```

**Note implementative:**

1. **vercel-action v25:** usa `amondnet/vercel-action` (alternativa consolidata
   per Action-based deploy). Se l'owner preferisce `vercel/action` ufficiale
   (richiede `vercel link` nel repo), sostituire. Entrambe leggono `vercel.json`
   in `working-directory`. [^src: management/kanban/EP-011-ci-cd/US-042-continuous-deployment-vercel/US-042.md §Acceptance Criteria]

2. **COOP/COEP:** `packages/app/vercel.json` contiene già gli header. Nessuna
   modifica al `vercel.json`. Il deploy NON deve sovrascrivere o ignorare
   il `vercel.json` (tutti i deploy Vercel da Action leggono il file se presente
   nella working directory del progetto — comportamento default).

3. **Segreti GitHub (gate umano):** il deployer deve creare manualmente su
   GitHub → Settings → Secrets and variables → Actions:
   - `VERCEL_TOKEN` (da vercel.com → Account Settings → Tokens)
   - `VERCEL_ORG_ID` (da `vercel env pull` o output di `vercel link`)
   - `VERCEL_PROJECT_ID` (idem)
   Senza i segreti il job fallisce con "secret not found" (non blocca TSK-049/CI).

4. **Condizionale prod/preview:** `startsWith(github.ref, 'refs/tags/v') && '--prod' || ''`
   aggiunge `--prod` solo sui tag `v*`. Su PR manca il flag → deploy di preview.

**Assunzione annotata:** l'azione `amondnet/vercel-action@v25` è scelta per
semplicità e uso consolidato. Se l'owner ha già un progetto Vercel linkato e
preferisce `vercel/action@v1` (GitHub App ufficiale), la struttura del workflow
cambia minimalmente (vercel-token + vercel-org-id + project-id rimangono, ma
il trigger `--prod` si gestisce via `scope` diverso). Annotare la preferenza
prima dell'implementazione.

## Decisioni implementative

- **Via di deploy scelta:** Vercel CLI ufficiale (`npx vercel@latest pull/build/deploy --prebuilt`) anziche' `amondnet/vercel-action@v25` (che la spec del TSK indicava come opzione). Rationale: supportata ufficialmente da Vercel, meno soggetta a deprecazioni di action di terze parti, comportamento esplicito (3 step distinti pull/build/deploy invece di un'action opaca).
- **Hardening CI/CD** (allineato a quanto richiesto in fase di review TSK-049):
  - `concurrency.group: cd-vercel-${{ github.ref }}` con `cancel-in-progress` true sulle PR e false sui tag.
  - `permissions: contents: read` a livello workflow (minimo necessario alla CLI Vercel — non commenta sulle PR).
  - `timeout-minutes: 15` sul job.
- **Condizionale prod/preview:** `startsWith(github.ref, 'refs/tags/v')` come da spec; `--prod` aggiunto solo sui tag, sia in `vercel build` che in `vercel deploy --prebuilt`. `vercel pull --environment=production|preview` distingue il pull delle env vars.

## Dependencies

[TSK-049] — il workflow CD non dipende tecnicamente dalla CI, ma la policy di
deploy ratificata prevede CI verde prima del deploy (verifica implicita via
branch protection su PR in TSK-050). Su tag, la CI è già passata sul commit
taggato.
