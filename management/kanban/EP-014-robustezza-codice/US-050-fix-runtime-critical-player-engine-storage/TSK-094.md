# TSK-094 — Atomicità putSaveState: try-unlink su fallimento manifest write

## Context

`putSaveState()` in `native-fs-adapter.ts:616-636` scrive il blob su disco (`[^src5: packages/app/src/storage/native-fs-adapter.ts:616]`) e poi aggiorna il manifest. Se il processo viene interrotto tra le due operazioni (crash, quota disco piena, errore IPC), il blob rimane su disco come orfano permanente: non è accessibile dalla UI, non è eliminabile dall'utente, e si accumula nel tempo.

Finding: P3-12 (major, conf. 0.85) da `soliboy-code-review-deep.md`.

Pattern di fix: write-then-manifest con cleanup nel catch. Se il manifest write fallisce dopo il blob write, invocare `tryUnlink(blobPath)` (best-effort) nel blocco `catch`, poi propagare l'errore originale al chiamante.

## Acceptance Criteria

1. `putSaveState()` in `native-fs-adapter.ts` avvolge la scrittura blob + manifest in un
   try/catch atomico.
2. Se la scrittura del manifest fallisce dopo che il blob è stato scritto, il codice
   tenta `tryUnlink(blobPath)` (best-effort — un fallimento di unlink è loggato ma non
   aggiunto all'errore propagato).
3. L'errore originale del manifest write è propagato al chiamante (non ingoiato).
4. In condizione nominale (entrambe le operazioni riuscite) il comportamento è identico
   a prima.
5. Test unitario (mock FS): scenario "blob write OK, manifest write throw" → `putSaveState`
   rigetta + `tryUnlink` invocato con il path del blob scritto. Verificabile tramite
   spy sul metodo di unlink dell'adapter.

## DoD

- [ ] `putSaveState` in `native-fs-adapter.ts` implementa il pattern try-unlink nel catch
- [ ] Errore originale propagato al chiamante
- [ ] Test unitario per lo scenario di fallimento manifest scritto
