# US-051 — Fix stale closure: FileLoader URI handler + App.tsx useMemo + Error Boundary

**Come** utente che importa una ROM da Capacitor URI o naviga tra le tab dell'app  
**voglio** che gli handler degli eventi siano sempre aggiornati e che un errore
nell'inizializzazione dell'adapter non lasci l'app bianca senza fallback  
**in modo da** poter usare le funzionalità senza dover ricaricare la pagina o
veder crash dell'intera applicazione.

## Contesto

Quattro finding `major` correlati riguardano la gestione delle closure React e
l'inizializzazione difensiva:

- **P1-04 (major, conf. 0.90)** — `FileLoader.tsx:93-104` registra `handleCapacitorUri`
  con deps `[]`: cattura `storage`, `onImported`, `_filesystemApi` come stale closure.
  Se cambiano dopo il mount (es. hot-reload, test con props diverse) il handler
  registrato resta obsoleto e usa adapter/callback vecchi.
- **P1-01/P1-02 (minor x2, conf. 0.85)** — `App.tsx:102-105` e `App.tsx:114` creano
  `videoPort` e `themePort` con `useMemo(() => makeXxxPort(selectedConfig), [])`:
  deps vuote ma `selectedConfig` è una dipendenza catturata stale. React eslint-hooks
  lo segnalerebbe come exhaustive-deps warning.
- **P3-01 (major, conf. 0.85)** — `App.tsx:55-60` chiama `selectAdapter()` a module-load
  fuori da qualsiasi componente React: una eccezione (es. `window.soliboyDesktop`
  corrotto, errore in `NativeFsAdapter` init) blocca l'intera app senza Error Boundary.
- **P3-03/P3-04 (major+minor, conf. 0.85/0.80)** — `FileLoader.tsx:67-73` `handleFile`
  async senza try/catch: errori runtime inattesi da `importRom` (TypeError, errore IDB
  non strutturato) diventano Promise rejected non gestite.

## Business Rules

- Handler di eventi globali (Capacitor URI, visibilitychange) devono usare reference
  stabili (useRef) per evitare stale closure su prop mutabili.
- L'inizializzazione dell'adapter di storage non deve mai produrre crash totale
  dell'app: un fallback (Error Boundary o lazy init con catch) deve presentare un
  messaggio di errore comprensibile.
- Tutti gli handler async invocati come `void` o da onChange devono avere try/catch
  interno che aggiorna lo state di errore in UI.

## Acceptance Criteria

1. `FileLoader` registra l'URI handler Capacitor usando un pattern stabile (useRef +
   funzione ref-setter, o useCallback inclusa nelle deps) — un cambio di prop
   `storage`/`onImported` aggiorna l'handler attivo senza re-registrare il listener.
2. `App.tsx` `videoPort` e `themePort` sono stabili rispetto a `selectedConfig`:
   o le deps sono complete, o la porta è creata via useRef con re-init esplicito al
   cambio adapter.
3. `selectAdapter()` è invocato in modo difensivo: una eccezione mostra un fallback
   UI ("Impossibile inizializzare lo storage — ricaricare l'app") invece di white
   screen. Il fallback è raggiungibile sia tramite Error Boundary React sia tramite
   try/catch nel componente App.
4. `handleFile` in FileLoader avvolge `importRom` in try/catch: errori runtime
   inattesi aggiornano `error` state con messaggio "Errore inatteso durante
   l'importazione — riprovare". L'errore è loggato in console (dev).
5. Test di regressione: hot-reload / React Strict Mode double-mount di FileLoader
   non causa handler stale (verifica con un mock di `storage` che cambia tra mount).
6. Test di regressione: `selectAdapter` mock che lancia → app mostra fallback,
   non bianco.
