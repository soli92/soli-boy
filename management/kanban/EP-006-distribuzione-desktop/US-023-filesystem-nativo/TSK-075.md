# TSK-075 — listRoms lazy: evitare materializzazione eager dei blob

## Context

Finding **F-2** del code-review di TSK-054 (`code_quality/reports/TSK-054-iter-1.json`):
`NativeFsAdapter.listRoms` materializza tutti i blob via `Promise.all(map(materializeRom))`,
emettendo un `readFile` IPC per ogni ROM. La Library UI usa solo i metadati: l'I/O eager dei
blob binari è overhead puro su desktop (N round-trip IPC). `IndexedDBAdapter` non paga lo stesso
costo perché ritorna il record atomicamente, ma l'interfaccia `StoragePort` non distingue
metadati da blob. [^src: code_quality/reports/TSK-054-iter-1.json §F-2]

## Technical Specs

- Decisione di design richiesta sull'interfaccia `StoragePort` (`packages/app/src/storage/port.ts`):
  - **Opzione A**: nuovo metodo `listRomsMeta(): Promise<RomMeta[]>` che ritorna solo i campi
    non-blob (additivo, non breaking).
  - **Opzione B**: flag `listRoms(opts?: { includeBlobFields?: boolean })` (default `false`).
  - Preferire l'opzione che minimizza il blast radius sui consumer (Library UI, export US-019).
- Implementare il path lazy in **entrambi** gli adapter (`native-fs-adapter.ts`,
  `indexeddb-adapter.ts`) mantenendo la parità semantica.
- Aggiornare i consumer di dominio che listano ROM per la UI a usare il path metadata-only.

## Blast radius / coordinamento

- Tocca `port.ts` + `indexeddb-adapter.ts` + `native-fs-adapter.ts` + `index.ts` e i consumer.
- **Schedulare dopo TSK-055** (selezione runtime adapter) per evitare edit concorrenti su
  `src/storage/index.ts` (vedi task-package F-2 nel report di review).

## DoD
