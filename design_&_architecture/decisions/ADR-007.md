# ADR-007 — Packaging Electron multipiattaforma con electron-builder

## Contesto

L'EP-006 richiede la distribuzione del prodotto come applicazione desktop nativa multipiattaforma, con accesso al filesystem nativo (US-023), core di emulazione inclusi localmente per uso offline (US-024) e aggiornamento automatico (US-025). [^src: management/kanban/EP-006-distribuzione-desktop/EP-006.md §Obiettivo]

Lo stack vincola la shell desktop a **Electron** (`raw/tech_stack.md` — "Shell desktop: Electron — Filesystem nativo, IPC, packaging, core offline"). La codebase è già una SPA Vite + React 18 + TypeScript in monorepo (`packages/app/`, [[ADR-001]]); la build web esistente produce `dist/` statico, già deployato su Vercel con header COOP/COEP (`packages/app/vercel.json`).

Il `StoragePort` astrae la persistenza con due adapter ([[ADR-002]]): `IndexedDBAdapter` per web/mobile, `NativeFsAdapter` per desktop via IPC. La toolchain di packaging deve quindi (a) confezionare la SPA in un contenitore Electron, (b) ospitare il processo main + preload con bridge IPC verso `NativeFsAdapter`, (c) bundlare localmente i core WASM (WasmBoy/mGBA, [[ADR-005]]) come asset offline, (d) produrre installer firmabili per Windows/macOS/Linux. [^src: management/kanban/EP-006-distribuzione-desktop/US-024-core-offline/US-024.md §Acceptance Criteria]

Gap aperto in `wiki/gaps.md` (`electron-packaging-toolchain`): toolchain non specificata, candidati Electron Forge / electron-builder / setup custom.

## Decisione

Si adotta **electron-builder** come unica toolchain di packaging per la versione desktop di soli-boy.

### Layout monorepo

Si introduce un workspace dedicato `packages/desktop/` (sibling di `packages/app/`) che ospita:

- `electron/main.ts` — processo main (window lifecycle, IPC server-side, integrazione `electron-updater` per ADR-008).
- `electron/preload.ts` — script preload con `contextBridge` che espone l'API IPC sicura usata da `NativeFsAdapter` (open/save dialog, read/write/list file ROM, save state, SRAM su filesystem nativo).
- `electron-builder.yml` — configurazione di packaging.
- `package.json` — dipendenze `electron`, `electron-builder`, `electron-updater` (vedi [[ADR-008]]).

Il renderer è la SPA esistente: la build `packages/app/` produce `dist/` (già funzionante per il web) e `packages/desktop/` la consuma come asset statico via `files` di electron-builder (`from: ../app/dist`). Nessuna modifica al bundler della SPA: lo stesso artefatto `dist/` è caricato dal browser via Vercel e da Electron via `file://` (o `app://` custom protocol per evitare quirk path).

### Configurazione electron-builder

- **Target multipiattaforma** (RF-23..RF-25, vincolo "pacchetti Win/macOS/Linux" da `raw/tech_stack.md`):
  - Windows: `nsis` (installer) — supporta auto-update via electron-updater (modalità per-user, no admin required).
  - macOS: `dmg` + `zip` (lo `zip` è il formato consigliato da electron-updater per il delta su mac); architetture `x64` + `arm64` (Apple Silicon).
  - Linux: `AppImage` (universale, auto-update supportato da electron-updater) + `deb` (per Debian/Ubuntu); `x64` baseline.
- **Asset locali offline (US-024)**: i core WASM (`wasmboy`, `@thenick775/mgba-wasm`) sono già installati come dipendenze npm e finiscono nel bundle Vite via `import` ESM; sono quindi parte di `packages/app/dist/` e bundleati automaticamente come asset statici. Nessun `extraResources` necessario per i core (gli engine sono in-bundle, vedi [[ADR-005]]). `extraResources` resta disponibile per eventuali ROM/BIOS di esempio o asset binari che NON devono passare per il bundler (non previsto al lancio, R.2).
- **App id**: `com.soli92.soliboy` (convenzionale reverse-DNS, owner-verificabile prima del primo signing).
- **Productname / artifactName**: `Soli-Boy-${version}-${os}-${arch}.${ext}`.
- **`asar: true`** — pacchettizzazione standard del bundle; `asarUnpack` riservato a eventuali binari nativi futuri (non previsti al lancio).
- **`publish`**: provider `github` con `owner: soli92`, `repo: soli-boy` — i metadata di update (`latest.yml`, `latest-mac.yml`, `latest-linux.yml`) e gli installer firmati sono pubblicati come asset di GitHub Release ad ogni tag `v*` (allineato alla policy CD esistente per Vercel, vedi gap chiuso `vercel-deploy-trigger-policy`). Dettaglio del meccanismo update in [[ADR-008]].

### Cross-Origin Isolation in Electron

I core WASM threaded richiedono COOP/COEP anche in Electron (vincolo `raw/tech_stack.md` — "per i core WASM con threading, header COOP/COEP sul server web"). In Electron lo schema di caricamento è `file://` (o protocollo custom): la cross-origin isolation va abilitata via:

- `session.defaultSession.webRequest.onHeadersReceived` nel main process, iniettando `Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp` su ogni risposta locale, OR
- registrazione di un **custom protocol** `app://` con `protocol.registerSchemesAsPrivileged([{ scheme: 'app', privileges: { secure: true, corsEnabled: true, supportFetchAPI: true } }])` che serve il `dist/` con gli header desiderati.

Soluzione preferita: **custom protocol `app://`** — evita le quirk di sicurezza di `file://` (es. fetch/CORS) e dà un punto unico per controllare gli header. Decisione implementativa di dettaglio rinviata al TSK di TPM (TSK-053 main process).

### Pipeline di build

- Comando in `packages/desktop/package.json`:
  - `build:web` → `npm -w @soli-boy/app run build` (produce `packages/app/dist/`).
  - `build:desktop` → `electron-builder --win --mac --linux` (CI) oppure target singolo locale (`--win`, `--mac`, `--linux`).
  - `dev:desktop` → avvia `vite dev` di `packages/app/` + `electron .` con `loadURL(http://localhost:5173)`.
- Il workflow GitHub Actions esistente (TSK-049) viene esteso con un job `desktop-release` triggherato su tag `v*`, runner matrix `windows-latest / macos-latest / ubuntu-latest`. Dettaglio TSK a cura del TPM.

### Code signing

- **macOS**: prerequisito **human** (R.14) — account Apple Developer Program ($99/anno), Developer ID Application certificate + notarization (Apple ID + app-specific password o API key in segreti GitHub Actions: `CSC_LINK`, `CSC_KEY_PASSWORD`, `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID`). electron-builder gestisce notarization via `notarize: true` quando le credenziali sono presenti.
- **Windows**: prerequisito **human** (R.14) — certificato Code Signing OV/EV da CA pubblica (DigiCert/Sectigo/…); segreti `CSC_LINK` + `CSC_KEY_PASSWORD`. Senza firma EV, SmartScreen mostra warning fino a "maturazione" reputazione.
- **Linux**: nessuna firma obbligatoria; AppImage unsigned è accettato dalla maggior parte dei desktop environment. Opzionale: firma GPG dei pacchetti.
- **Stato iniziale tollerato**: il primo release può essere prodotto **unsigned** (build verde, installer funzionanti, warning di sicurezza visibili agli utenti). Firma codice = follow-up tracciato come prerequisito human nel TSK di rilascio (gate umano R.14). Il design degli ADR-007/008 non cambia in funzione della firma: i flag di signing si attivano quando i segreti sono presenti, senza modifiche architetturali.

## Conseguenze

### Positive

- **Continuità**: nessuna modifica al bundler Vite della SPA (`packages/app/vite.config.ts` intatto); il `dist/` web è riutilizzato 1:1 dal renderer Electron.
- **Offline (US-024)**: i core WASM sono già nel bundle ESM via `wasmboy` / `@thenick775/mgba-wasm` (dipendenze npm di `packages/app/`), quindi inclusi automaticamente nell'installer Electron senza configurazione speciale.
- **Coerenza CD**: stesso trigger (`tag v*`) per web (Vercel) e desktop (GitHub Releases) — un unico modello di rilascio per l'owner.
- **Sinergia con auto-update**: electron-builder genera in build i metadata richiesti da electron-updater ([[ADR-008]]) — zero overhead di configurazione cross-tool.
- **Filesystem nativo (US-023)**: il preload + IPC abilita il `NativeFsAdapter` previsto da [[ADR-002]] senza disturbare il dominio (la `StoragePort` non cambia).
- **Cross-platform**: copertura Win/macOS/Linux con un'unica config dichiarativa.

### Negative / rischi

- **Code signing = costo + identità owner**: per macOS è quasi obbligatorio (Gatekeeper); per Windows è fortemente raccomandato (SmartScreen). Stato iniziale unsigned è tollerato ma sub-ottimale. **Prerequisito human**, non risolvibile in design.
- **Bundle size**: l'installer include Electron runtime (~80-100 MB compresso). Inevitabile dato il vincolo stack "Shell desktop: Electron".
- **CI matrix triplice**: Win/macOS/Linux runner aumentano i minuti CI. Mitigazione: job desktop-release solo su tag `v*`, non su ogni PR.
- **Notarization macOS**: latenza in build (1-10 min di attesa di Apple). Accettabile per release su tag.
- **Aggiornamenti macOS App Store**: fuori scope (US-025 prevede auto-update diretto, non Store distribution). Mac App Store richiederebbe sandbox + provisioning diversi — non in EP-006.

### Invariante

- I dati restano on-device (US-033, [[ADR-002]]): l'auto-update tocca solo il binario applicativo, MAI i file utente (ROM/save/SRAM/config), che vivono sotto `app.getPath('userData')` separato dall'app bundle.
- Nessuna ROM/BIOS protetto incluso negli installer ([[ADR-003]] vincolo legale): gli installer contengono solo codice applicativo + core WASM open source.

## Alternative considerate

### Electron Forge (scartata)

Toolchain ufficiale Electron, integra bundler (Webpack/Vite plugin), packager, maker e publisher in un'unica CLI.

- **Pro**: monorepo-friendly, plugin Vite ufficiale, ecosistema "blessed" da Electron team, auto-update via `update.electronjs.org` (servizio gratuito hosted).
- **Contro**:
  1. Il plugin Vite di Forge **gestisce esso stesso** il bundling, duplicando o sovrascrivendo la config Vite esistente di `packages/app/` (che oggi ha COOP/COEP custom e setup vitest/playwright). Migrare significa rischiare regressioni su un setup verde.
  2. L'auto-update via Forge è legato a Squirrel (Windows/macOS) + `update.electronjs.org` (server gestito da Electron team, free tier ma con limiti e nessuna garanzia di SLA per progetti privati). Linux auto-update via Squirrel non è supportato → richiede comunque un secondo meccanismo.
  3. Ecosistema updater più frammentato rispetto al binomio electron-builder + electron-updater (che copre tutti e tre i target con un solo client e un solo formato di metadata).

Per soli-boy il valore aggiunto di Forge (bundler integrato) NON è rilevante perché la SPA è **già bundleata** da Vite con config consolidata; il costo della migrazione supera il beneficio.

### Setup custom (scartata)

Compilare a mano con `electron-packager` + script bash + zip manuali.

- **Pro**: zero dipendenze "magiche".
- **Contro**: re-implementazione da zero di feature standard (NSIS installer, DMG layout, AppImage, code signing pipelines, auto-update metadata). Over-engineering rispetto a un problema risolto da electron-builder. Violazione del principio "soluzione proporzionata alla complessità".

### Tauri (fuori scope)

Alternativa moderna a Electron (Rust + WebView nativa).

- **Contro decisivo**: viola `raw/tech_stack.md` ("Shell desktop: Electron"). PATTERN §11 — tecnologie esplicitate nei requisiti = obbligatorie, non sostituibili. Non considerata.

## Pending / follow-up

- TSK-053 (main process): scelta finale tra `file://` + onHeadersReceived vs custom protocol `app://` per COOP/COEP — entrambe valide, decisione di dettaglio in implementazione.
- Acquisizione certificati di firma codice: **prerequisito human** (R.14), non bloccante per il primo release unsigned.
- Sandbox Electron + `contextIsolation: true` + `nodeIntegration: false`: default sicuri, da rispettare nel TSK-053. Il preload espone solo le primitive IPC necessarie a `NativeFsAdapter`.
