# ADR-065 — Acceptance-spec del Functional Oracle: schema (framework) vs contenuto (progetto)

## Contesto

Il functional oracle (EP-018) deve verificare che l'app **faccia la cosa per cui esiste**. Ma il
meta-framework è agent-agnostic: non può sapere che soli-boy è un emulatore, né cosa significhi «il
gioco parte». Definire «pass funzionale» nel framework sarebbe sbagliato (domain leak); non definirlo
affatto renderebbe l'oracolo inutile. Stessa tensione già risolta altrove: `ux_ui.design_system_path`
(il framework definisce *come* leggere un DS, il progetto fornisce *quale*), e l'acceptance dei test
(il framework fornisce il runner, il progetto i test).

## Decisione

**Separazione schema/contenuto, con primitive di asserzione domain-agnostic.**

### A. Il framework possiede SCHEMA + ENGINE

- **Schema** dell'`acceptance-spec` (versionato nel framework, validato dalla skill).
- **Engine** di esecuzione: Playwright via Bash (ADR-008) + app-lifecycle serve (ADR-064) + cattura
  evidenza (ADR-017). Nessuna logica di dominio.

### B. Il progetto possiede il CONTENUTO

L'`acceptance-spec` vive nel **progetto**, referenziato dal TSK (`functional_acceptance_spec:`) o
per-app in `code_quality/acceptance/<app|tsk>.acceptance.yaml`. Schema:

```yaml
fixtures:                       # input reali da caricare (artefatti del progetto)
  - id: test-rom
    path: packages/app/public/test-roms/<homebrew-legale>.gba
    load_via: { selector: "input[type=file]", action: set_input_files }
scenario:                       # passi di interazione (vocabolario condiviso — ADR-066)
  - { action: click, selector: "[data-test=load-rom]" }
  - { action: wait_for, selector: "canvas", state: visible, timeout_ms: 10000 }
  - { action: wait_ms, value: 2000 }
assertions:                     # esiti OSSERVABILI, ciascuno con severità
  - { id: canvas-advancing, severity: blocking, kind: canvas_pixel_variance, selector: "canvas", min_variance: 0.02, frames: 8 }
  - { id: state-running,    severity: blocking, kind: attr_equals, selector: "[data-test=engine]", attr: "data-state", value: "running" }
  - { id: no-console-error, severity: advisory, kind: console_no_error }
  - { id: save-artifact,    severity: blocking, kind: storage_key_present, store: idb, key_glob: "savestate:*" }
thresholds: { advisory_max: 2 }
```

### C. Primitive di asserzione (domain-agnostic, fornite dal framework)

L'engine implementa un set chiuso di `kind` agnostici al dominio, componibili dal progetto per
esprimere significato di dominio:

| `kind` | Verifica (deterministica) |
|---|---|
| `selector_visible` / `selector_absent` | presenza/visibilità DOM |
| `attr_equals` / `text_matches` | transizione di stato osservabile via attributo/testo |
| `canvas_pixel_variance` | il canvas mostra contenuto **che cambia** tra N frame (≥ min_variance) → copre «emulazione/video sta girando» senza conoscere il gioco |
| `storage_key_present` | artefatto creato in localStorage/IDB/fs (es. save-state) |
| `console_no_error` / `network_no_5xx` | nessun errore runtime durante lo scenario |

Il progetto **compone** queste primitive; il framework non aggiunge mai semantica di dominio.

### D. Semantica di «pass» a severità (riuso CQRL/EP-005)

- Tutte le asserzioni `blocking` passano → **pass**.
- Solo `advisory` falliscono (entro `advisory_max`) → **conditional**.
- Una qualsiasi `blocking` fallisce (o `advisory` oltre soglia) → **reject**.

Allineato al verdict tier di EP-005 (ADR-012) e CQRL.

### E. Assenza di acceptance-spec

- `functional_oracle.enabled: false` (default) → capability spenta, no-op (R.P3).
- `enabled: true` **e** spec assente/illeggibile → **fail-loud** (config incoerente: hai optato in
  senza fornire il contratto). MAI un pass silenzioso (anti-fabbricazione, ADR-063/064).
- Spec presente ma vuota/`scenario: []` → verdict `skip` **dichiarato** (non pass).

## Rationale

1. **Agent-agnostic preservato.** Le primitive sono DOM/canvas/storage/console — universali; il
   dominio vive nella composizione, di proprietà del progetto. Stesso principio di
   `design_system_path` e dei test del progetto.
2. **`canvas_pixel_variance` è la chiave per le app «a tela»** (emulatori, giochi, video, grafica):
   «il pixel cambia nel tempo» è una prova funzionale forte e domain-agnostic, che uno screenshot
   statico (EP-005/EP-008) non può dare.
3. **Deterministico = anti-fabbricazione.** Il verdict nasce da asserzioni binarie, non da giudizio
   LLM (vedi ADR-067): un oracolo non può «inventare» un pass.

## Conseguenze

- **Positive**: «pass funzionale» diventa definibile e verificabile senza domain leak nel framework.
- **Costi**: il progetto deve scrivere e mantenere l'acceptance-spec + fornire fixture (ADR-066 §E
  EP-018 per le licenze). Il framework valida lo schema e fa fail-loud sulle incongruenze.
- **Storage/frontmatter** (riuso ADR-012): report
  `code_quality/reports/<TSK-id>-functional-iter-<N>.{json,md}` + cartella trace/screenshot;
  frontmatter TSK opzionale `functional_status:` (single-writer skill) + `functional_acceptance_spec:`
  (path, scritto dal TPM/progetto).
