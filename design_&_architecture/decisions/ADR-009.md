# ADR-009 — RTC dell'emulatore: piattaforme, payload, schema, bridge, policy

## Contesto

EP-019 introduce il controllo utente dell'orologio interno (Real Time Clock, RTC) dell'emulatore: impostazione data/ora dal Settings (US-065), persistenza locale dello stato fra sessioni (US-066), inclusione nei save state (US-067), riallineamento all'orologio del dispositivo (US-068). [^src: management/kanban/EP-019-rtc-orologio-interno/EP-019.md §Storie incluse]

Le US sono scritte tecnologia-agnostiche ("orologio interno", "stato dell'orologio", "orologio del dispositivo"). Il "come" — mappa piattaforma↔RTC, formato del payload atteso dai core, schema di persistenza, interfaccia di bridge engine↔dominio, policy di drift/timezone — non era documentato in wiki ed è tracciato in `wiki/gaps.md` come gap non-bloccante `rtc-real-time-clock-piattaforme-e-giochi` (apertura 2026-06-30). [^src: wiki/gaps.md §2026-06-30 10:00 — rtc-real-time-clock-piattaforme-e-giochi]

Le piattaforme supportate al lancio (GB/GBC via Gambatte/WasmBoy, GBA via mGBA, arcade FBNeo/MAME via futura EP-009) hanno comportamenti differenti rispetto all'RTC: non tutte espongono un orologio interno, e fra quelle che lo fanno il formato di serializzazione interno al core è diverso. [^src: design_&_architecture/decisions/ADR-005.md §Decisione]

Il modello di persistenza esistente prevede quattro object store IndexedDB (`roms`, `saveStates`, `sram`, `config`) con `romId` come chiave logica di associazione al gioco e cascade-delete su `removeRom`. L'RTC va innestato in questo modello come quinto dato del gioco, distinto da SRAM e save state come richiesto da US-066 (Business Rule "terza categoria di dato del salvataggio del singolo gioco"). [^src: design_&_architecture/db_schemas/indexeddb-stores.md §Object stores]

L'astrazione `EmulatorEngine` (ADR-003) consente di mantenere il dominio agnostico rispetto al formato raw dei core: la traduzione fra modello canonico di dominio (`RtcState`) e formato raw engine-specifico (registri MBC3 / sequenza BCD GBA) è collocata negli adapter (`WasmBoyEngine`, `MgbaEngine`). [^src: design_&_architecture/decisions/ADR-005.md §Decisione]

## Decisione

### 1. Mappa piattaforma ↔ presenza RTC

| Piattaforma | Core / Adapter | RTC nativo della piattaforma | Detection runtime | Note |
|---|---|---|---|---|
| **GB (DMG)** | Gambatte via `WasmBoyEngine` | NO | — | Mapper MBC1/MBC2/MBC5 senza orologio. |
| **GBC** | Gambatte via `WasmBoyEngine` | SÌ, **solo su cartucce MBC3+RTC** | Header ROM byte `0x0147 ∈ {0x0F, 0x10}` (MBC3+TIMER+BATTERY / MBC3+TIMER+RAM+BATTERY) | Titoli noti: Pokémon Oro/Argento/Cristallo, Harvest Moon GBC. |
| **GBA** | mGBA via `MgbaEngine` | SÌ, **solo su cartucce con chip RTC Seiko S-3511A** | Detection mGBA via override database / pattern memory match | Titoli noti: Pokémon Rubino/Zaffiro/Smeraldo, Boktai. |
| **Arcade** | FBNeo/MAME (gap `arcade-emulation-engine`) | **fuori scope EP-019** | — | Rinviato a EP-009. |
| **Stub** (test) | `StubEngine` | NO di default, override per test | — | `StubRtcBridge` opzionale per scenari deterministici. |

La detection è **per-cartuccia, non per-piattaforma**: `hasRtc()` interroga l'engine concreto (che ispeziona l'header della ROM caricata), NON una lookup statica sulla piattaforma. Il fallback conservativo `hasRtc('gbc') = true` documentato in TSK-125 è una *temporary placeholder* per consentire lo sviluppo del dominio prima dell'implementazione dei bridge reali: viene sostituito da detection runtime via `RtcBridge.hasRtc()` non appena i bridge concreti sono implementati. [^src: management/kanban/EP-019-rtc-orologio-interno/US-065-impostare-data-ora-rtc/TSK-125.md §Technical Specs]

### 2. Formato payload `RtcState` (modello canonico di dominio)

Il dominio (`RtcService`, `GameSession`, `SaveService`, UI Settings) lavora **esclusivamente** sul modello canonico **wall-clock** definito in TSK-125:

```ts
type RtcState = {
  year: number;    // ≥ 2000, intero
  month: number;   // 1..12
  day: number;     // 1..31 (validato anche rispetto al mese/anno)
  hour: number;    // 0..23
  minute: number;  // 0..59
  second: number;  // 0..59
};
```

- **Semantica:** wall-clock UTC (vedi §5).
- **Senza timezone:** l'RTC dell'hardware emulato è un orologio "muro" senza concetto di zona — il timezone è gestito solo nel form UI Settings (conversione locale ⇄ UTC al momento del rendering, non persistita).
- **Senza giorno della settimana:** il `dayOfWeek` (richiesto da S-3511A su GBA) è derivato deterministicamente dalla data nel bridge GBA — non è parte del modello canonico.
- **Senza sub-second precision:** la granularità minima è il secondo, coerente con la precisione dei chip RTC reali.

#### Formati di serializzazione engine (interni ai bridge)

I formati raw NON sono esposti al dominio. La traduzione è collocata negli adapter `EmulatorEngine`:

- **Gambatte / MBC3 (`WasmBoyRtcBridge`):**
  - 5 registri MBC3: `RTC_S` (secondi 0–59), `RTC_M` (minuti 0–59), `RTC_H` (ore 0–23), `RTC_DL` (day counter low, 8 bit), `RTC_DH` (bit 0 = day counter high, bit 6 = halt flag, bit 7 = day carry flag).
  - `latchedTime`: epoch seconds (UTC) — riferimento temporale per il calcolo del day counter MBC3.
  - **Encoding:** `RtcState` → epoch seconds UTC → delta dal `latchedTime` → registri MBC3. Decoding inverso.
  - Il bridge espone solo `getRtcState() / setRtcState()`: la gestione di `halt` (registro fermo) e `carry` (overflow giorni) è interna al core Gambatte e non parte del modello canonico.

- **mGBA / GBA (`MgbaRtcBridge`):**
  - Sequenza 7-byte BCD: `year` (00–99 = 2000–2099), `month` (01–12), `day` (01–31), `dayOfWeek` (0–6), `hour` (00–23), `minute` (00–59), `second` (00–59).
  - **Encoding:** `RtcState` → 7-byte BCD (con `dayOfWeek` calcolato deterministicamente da `(year, month, day)` con algoritmo Zeller o equivalente). Decoding inverso.
  - L'anno `1900+year` di S-3511A non è ambiguo nel range [2000, 2099] dell'epoca soli-boy.

- **`StubRtcBridge` (test):** memoria in-process, restituisce/accetta `RtcState` senza trasformazione. Comportamento override-abile in test.

### 3. Schema IndexedDB — nuovo store `rtcState`

Estensione del modello in `design_&_architecture/db_schemas/indexeddb-stores.md`. **Quinto object store**, distinto da `sram` e `saveStates` come richiesto da US-066 Business Rule "terza categoria di dato".

```
Store: rtcState
  keyPath: romId
  Campi:
    romId: string              // FK logica → roms.id (cascade-delete)
    state: RtcState            // modello canonico (vedi §2)
    updatedAt: string          // ISO 8601 UTC, es. "2026-06-30T12:34:56.000Z"
    schemaVersion: number      // = 1 (riservato per future migration)
  Index: nessuno (accesso sempre per romId)
```

- **Versione database:** bump da versione corrente a versione +1 in `onupgradeneeded` (`createObjectStore('rtcState', { keyPath: 'romId' })`).
- **Cascade delete:** `removeRom(romId)` chiama `deleteRtcState(romId)` insieme alle altre rimozioni (SRAM, save states), conformemente a US-066 AC "rimuovendo la ROM dalla libreria, lo stato dell'orologio interno associato viene rimosso".
- **`NativeFsAdapter` (desktop Electron, ADR-007):** mappatura su file `<romId>.rtc.json` nella directory dati di gioco, analogamente a SRAM. Implementazione stub in TSK-127 (ADR-pending → ADR-009 chiuso, ora `// planned: allineamento NativeFs piena implementazione`).
- **Inclusione nei save state:** campo opzionale `rtcState?: RtcState` aggiunto alla entry `saveStates`. **Nessun bump versione IDB** richiesto: IndexedDB è schema-less per campi non-keyPath/non-index. Compat all'indietro: entry preesistenti senza il campo restano valide (US-067 AC "save state creati prima dell'introduzione di questa storia restano caricabili").

#### Operazioni `StoragePort`

```ts
interface StoragePort {
  // ... operazioni esistenti
  putRtcState(romId: string, state: RtcState): Promise<void>;
  getRtcState(romId: string): Promise<RtcState | null>;
  deleteRtcState(romId: string): Promise<void>;  // idempotente
}
```

`updatedAt` e `schemaVersion` sono gestiti internamente dall'adapter (`Date.now().toISOString()`, `schemaVersion = 1`) e non esposti al dominio.

### 4. Interfaccia engine↔RTC bridge

Contratto TypeScript vincolante:

```ts
interface RtcBridge {
  /** Detection runtime: true se la cartuccia caricata ha un chip RTC. */
  hasRtc(): boolean;

  /** Legge lo stato corrente dal core. null se hasRtc=false o RTC non latched. */
  getRtcState(): RtcState | null;

  /** Applica live al core lo stato impostato dall'utente. No-op se hasRtc=false. */
  setRtcState(state: RtcState): void;
}
```

- Esposto da `EmulatorEngine` come campo opzionale `rtcBridge?: RtcBridge | null`.
- Implementazioni concrete previste:
  - `WasmBoyRtcBridge` (in `core/wasmboy-rtc-bridge.ts`): incapsula MBC3 registers ↔ `RtcState`.
  - `MgbaRtcBridge` (in `core/mgba-rtc-bridge.ts`): incapsula S-3511A BCD ↔ `RtcState`.
  - `StubRtcBridge` (in `core/stub-engine.ts`): in-memory per test deterministici.
- I bridge concreti sono **TSK distinti**, fuori dallo scope della wave EP-019 Sprint 15. Gli stub `rtcBridge = null` nei TSK-128 restano validi: la pipeline `GameSession` (persist on stop / restore on start) e `SaveService` (snapshot include RTC) gira a vuoto finché `rtcBridge` è null (no-op silenzioso, comportamento già pianificato come "best-effort").
- Quando i bridge reali vengono implementati (TSK futuri post-Sprint 15), il dominio NON cambia: cambia solo l'inizializzazione di `engine.rtcBridge` in `WasmBoyEngine` / `MgbaEngine`.

### 5. Policy drift, timezone, riallineamento

| Aspetto | Decisione | Razionale |
|---|---|---|
| **Timezone canonico** | **UTC** sul persisted state. Conversione locale ⇄ UTC solo nel form UI Settings (rendering time). | Evita ambiguità (cambio fuso del dispositivo non riscrive lo stato persistito); coerente con epoch-based MBC3. |
| **Pausa** | **Freeze** (no tick) | Coerente con l'aspettativa utente "pausa = sospensione totale". Implementato sospendendo il clock dell'engine (Gambatte/mGBA tickano l'RTC sul ciclo emulato, che si ferma in pausa nativamente). |
| **Drift fra sessioni** | **Freeze on close, resume from stored state** | Alla riapertura il gioco riparte dall'esatto `state` persistito. Nessun catch-up automatico al wall-clock corrente. Coerente con US-066 AC "non riparte da un valore non controllato". |
| **Tick durante esecuzione** | Demandato all'engine | Gambatte/mGBA tickano internamente in base al ciclo emulato — comportamento nativo dei core, non sovrascritto dal dominio. |
| **Sync to device (US-068)** | **Esplicito + locale only** | L'azione `RtcService.syncToDevice()` legge `Date.now()` locale al click, converte a `RtcState` UTC, chiama `setRtcState`. **Nessuna chiamata di rete** (vincolo RNF-05 sicurezza + RNF-06 privacy). |
| **Sync automatico all'avvio?** | **NO** | US-068 Business Rule esplicita: "l'apertura del Settings, l'avvio del gioco, il caricamento di una ROM e la ripresa da pausa non riallineano l'orologio interno". |
| **Validazione** | Range check + giorni-per-mese | `validateRtcState` (TSK-125) verifica range base; il dominio in EP-019 può tollerare giorno=31/febbraio (il core valida internamente). Hardening future: validazione calendar-aware. |

#### Conversione UTC ⇄ locale (UI Settings)

Il form Settings (TSK-126) presenta i campi nel **timezone locale del dispositivo** (più naturale per l'utente). La conversione avviene nel componente UI:

- **Lettura:** `RtcState` UTC → `Date` JS → display in `Intl.DateTimeFormat` locale.
- **Scrittura:** input utente locale → `Date` JS → `RtcState` UTC → `setRtcState`.

La conversione è **stateless** (deriva solo dal timezone corrente del dispositivo): non è persistita, non viene mai inclusa in `RtcState`.

## Conseguenze

### Positive

- **Dominio engine-agnostico**: `RtcState` canonico isola dominio/UI/test dai dettagli MBC3/S-3511A. Cambio del core (es. ADR-005 sostituzione futura di WasmBoy) non impatta dominio.
- **Compat all'indietro automatica**: campo `rtcState?` opzionale in `saveStates` significa che gli ~N save state preesistenti continuano a caricarsi senza modifiche (US-067 AC verificato by-design).
- **Privacy on-device garantita**: nessun campo del modello richiede o suggerisce sync con server esterni. Sync to device è locale-only by-spec (US-068, RNF-06).
- **Cascade delete coerente**: lo stato RTC segue lo stesso ciclo di vita di SRAM/save (rimozione ROM = rimozione completa), evitando entry orfane.
- **Estensibilità incrementale**: gli stub `rtcBridge = null` in WasmBoyEngine/MgbaEngine consentono di chiudere lo Sprint 15 (dominio + storage + Settings UI + save service) senza dover implementare i bridge concreti — TSK futuri per Pokémon GBC/GBA reali.
- **Cinque AC EP-019 coperti**:
  - US-065 (set) → `RtcService.setRtcState` + form UI.
  - US-066 (persist) → `StoragePort.putRtcState` + cascade delete.
  - US-067 (save state) → campo opzionale + compat all'indietro.
  - US-068 (sync to device) → `Date.now()` locale + esplicito.

### Negative / rischi

- **Bridge reali fuori scope Sprint 15**: gli e2e con ROM Pokémon reali (TSK-132 scenari 12–13) restano `test.skip` finché `WasmBoyRtcBridge` e `MgbaRtcBridge` non sono implementati. Mitigazione: copertura unit + e2e StubEngine garantisce il flusso dominio prima della verifica con core reali.
- **Day counter MBC3**: il modello canonico (`year/month/day`) sopprime il concetto di "day counter assoluto" di MBC3. Conversione bidirezionale via `latchedTime` epoch — corretta finché `year ≥ 2000`. Mitigazione: validazione esplicita in `RtcService.validateRtcState`.
- **Calendar-aware validation non implementata**: `validateRtcState` accetta 31/02 — il core MBC3/mGBA può comportarsi in modo non-deterministico su date impossibili. Mitigazione: documentazione utente + hardening follow-up.
- **Timezone shift utente**: se l'utente cambia timezone fra due sessioni, l'UI Settings mostra valori diversi pur essendo lo `state` UTC invariato. Mitigazione: documentazione/copy UI ("data e ora del dispositivo locale"); accettato come trade-off rispetto a memorizzare il timezone (che introdurrebbe ambiguità sul wall-clock dell'hardware).
- **Schema versioning**: `schemaVersion = 1` riservato ma non utilizzato in EP-019. Mitigazione: nessuna logica di migration necessaria al lancio; il campo esiste per future evoluzioni del payload.

### Invariante

- I dati RTC restano sul dispositivo come tutti gli altri dati di gioco (ADR-002 privacy on-device). Nessuna telemetria.
- L'ordering relativo dei dati di un gioco è invariato: ROM (immutabile) → SRAM (in-game) → save state (snapshot manuale) → RTC (terza categoria di salvataggio, US-066).

## Alternative considerate

### Modello canonico = epoch seconds (UTC) invece che wall-clock (scartata)

`RtcState = number` (epoch UTC seconds) sarebbe più compatto e zero-ambiguity sui timezone.

- **Pro**: minimalismo, una sola operazione di conversione (epoch ↔ MBC3/BCD).
- **Contro**:
  1. La form UI Settings (TSK-126) richiede comunque giorno/mese/anno/ora/min/sec separati per l'input utente → conversione extra non risparmiata.
  2. Validazione range (mese 1–12, ecc.) richiederebbe scomposizione comunque.
  3. Less readable in debug / IDB Inspector.

Scartata in favore del modello wall-clock già introdotto in TSK-125.

### Persistere il timezone in `RtcState` (scartata)

`RtcState = { ..., tz: string }` per registrare il fuso del dispositivo al momento dell'impostazione.

- **Pro**: l'utente vedrebbe sempre i valori "come li aveva inseriti" indipendentemente da cambi di fuso.
- **Contro**:
  1. L'hardware RTC reale (MBC3, S-3511A) NON ha concetto di timezone — è wall-clock. Memorizzarlo introduce un mismatch semantico fra dominio e hardware.
  2. Il cambio fuso del dispositivo (viaggi, modifica utente) genera ambiguità: il gioco deve vedere il fuso di registrazione o quello corrente?
  3. Over-engineering per un MVP single-player on-device.

Scartata. La conversione locale ⇄ UTC resta nel layer UI, stateless.

### Sync automatico all'avvio (scartata)

All'avvio del gioco, sincronizzare automaticamente l'RTC al wall-clock corrente.

- **Pro**: l'utente non deve mai preoccuparsi della data.
- **Contro**:
  1. Viola esplicitamente US-068 Business Rule.
  2. Rompe lo use-case principale (testare eventi temporali con date arbitrarie).
  3. Sorprende l'utente che ha impostato una data specifica per giocare un evento.

Scartata.

### Catch-up del tempo passato fra sessioni (scartata)

Alla riapertura, avanzare l'RTC del delta wall-clock fra chiusura e riapertura.

- **Pro**: simula un orologio "che continua a girare" anche con app chiusa.
- **Contro**:
  1. Viola US-066 AC "non riparte da un valore non controllato" (l'utente potrebbe aprire l'app dopo settimane e trovare eventi temporali "saltati").
  2. Richiede di persistere anche il wall-clock di chiusura (campo extra) e logica di delta.
  3. Per i giochi RTC-aware, l'utente può sempre cliccare "Usa ora del dispositivo" (US-068) per ottenere lo stesso effetto, esplicitamente.

Scartata. Comportamento freeze-on-close + sync-on-demand è semanticamente equivalente, esplicito, zero-sorprese.

### Bridge tramite save state blob esistente (scartata)

Includere lo stato RTC dentro lo `snapshotBlob` del save state, senza un campo dedicato.

- **Pro**: zero modifiche allo schema `saveStates`.
- **Contro**:
  1. Save state senza RTC corrente (`putSaveState` con bridge null) non distinguibile da save state pregresso → ambiguità su compat all'indietro.
  2. Il dominio dovrebbe deserializzare il blob (interno al core) per estrarre l'RTC → violazione encapsulation engine.
  3. Persistenza tra-sessioni (US-066) richiede comunque un canale dedicato a parte (non solo save state) → store dedicato `rtcState` necessario comunque.

Scartata. Il campo opzionale `rtcState?` nella entry `saveStates` è la soluzione minimale e ortogonale.

## Pending / follow-up

- **TSK Sprint 16 (proposti, fuori scope EP-019):**
  - `WasmBoyRtcBridge` reale: implementazione MBC3 registers ↔ `RtcState`.
  - `MgbaRtcBridge` reale: implementazione BCD S-3511A ↔ `RtcState`.
  - e2e con ROM Pokémon GBC/GBA (sblocca i `test.skip` di TSK-132 scenari 12–13).
- **Calendar-aware validation**: hardening di `validateRtcState` per rifiutare 31/02, 30/02 ecc.
- **Documentazione UI**: copy del form Settings deve esplicitare "data e ora del dispositivo locale" (mitigazione timezone shift) — di dettaglio in TSK-126.
- **Aggiornamento `design_&_architecture/db_schemas/indexeddb-stores.md`**: aggiungere il quinto store `rtcState` al documento (proposto come task wiki-keeper/architect post-merge ADR-009).
