# ADR-008 — Auto-update desktop con electron-updater + GitHub Releases

## Contesto

L'US-025 (priorità medium) richiede che la versione desktop si aggiorni automaticamente con tre criteri di accettazione: (a) l'app rileva la disponibilità di una nuova versione, (b) l'aggiornamento è applicabile senza reinstallazione manuale, (c) l'esito (successo/errore) è comunicato all'utente. [^src: management/kanban/EP-006-distribuzione-desktop/US-025-aggiornamento-automatico/US-025.md §Acceptance Criteria]

Il packaging è fissato da [[ADR-007]] su **electron-builder**, con publish su **GitHub Releases** (provider `github`) e artefatti `nsis` (Win), `dmg`+`zip` (macOS), `AppImage`+`deb` (Linux). I metadata di update (`latest.yml` / `latest-mac.yml` / `latest-linux.yml`) sono generati automaticamente da electron-builder ad ogni build di release e pubblicati come asset della Release.

L'infrastruttura GitHub è già operativa: repository `soli92/soli-boy`, workflow CI/CD attivo, policy CD su tag `v*` (gap chiuso `vercel-deploy-trigger-policy`). I tag `v*` guidano già il deploy web su Vercel — possono guidare anche il rilascio desktop senza introdurre nuovi trigger.

Gap aperto in `wiki/gaps.md` (`electron-autoupdate-mechanism`): meccanismo non specificato, candidati `electron-updater` / `@electron/update-electron-app` (Squirrel + `update.electronjs.org`) / Squirrel diretto / server custom.

## Decisione

Si adotta **`electron-updater`** (pacchetto npm della famiglia electron-builder) come client di auto-update, con **GitHub Releases come canale di distribuzione**.

### Architettura

1. **Server di distribuzione** = **GitHub Releases** del repo `soli92/soli-boy`.
   - Ogni tag `v*` produce una Release con installer firmati (quando i certificati sono disponibili, vedi [[ADR-007]]) + metadata YAML.
   - electron-builder con `publish: { provider: 'github', owner: 'soli92', repo: 'soli-boy' }` carica gli artefatti via API GitHub durante il job `desktop-release` (segreto `GH_TOKEN` con scope `public_repo`).
   - **Nessun server custom da gestire**: GitHub Releases assume il ruolo di CDN/registry di update — affidabile, gratuito per repo pubblici, già governato dal flusso di rilascio.

2. **Client di update** = `electron-updater` nel processo **main** Electron.
   - Modulo dedicato `electron/updater.ts` in `packages/desktop/` (vedi [[ADR-007]] §Layout monorepo).
   - API: `autoUpdater.checkForUpdatesAndNotify()` o `checkForUpdates()` + flusso manuale con eventi.
   - **Trigger di check**:
     - Automatico all'avvio (con piccolo delay, es. 10s, per non rallentare lo startup).
     - Periodico in background (intervallo conservativo, es. ogni 4-6 ore mentre l'app è aperta).
     - Manuale via voce di menu "Verifica aggiornamenti" (UX comune, da implementare).
   - **Flusso applicazione**:
     - `checking-for-update` → `update-available` (con versione + release notes) → `download-progress` (percentuale) → `update-downloaded` → l'utente conferma il riavvio → `autoUpdater.quitAndInstall()`.
     - `update-not-available` → no-op (eventualmente notificare solo sul check manuale).
     - `error` → notifica utente con messaggio non-tecnico + log nel diagnostic file (US-025 AC3).
   - **Modalità di applicazione**:
     - Windows (NSIS): update silenzioso scaricato in background, applicato al riavvio. NSIS perUserMode evita prompt UAC.
     - macOS (zip): update scaricato e applicato al riavvio via Squirrel.Mac (incluso in electron-updater).
     - Linux (AppImage): update scaricato e sostituito al riavvio (electron-updater supporta AppImage natively).
     - Linux (deb): **NON auto-updatable** da electron-updater (richiede `apt`/`dpkg` con privilegi). Per gli utenti deb, l'app rileva la nuova versione ma mostra un messaggio non-bloccante "Nuova versione disponibile — scarica da GitHub Releases" con link (US-025 AC1 soddisfatto, AC2 mitigato con esperienza degradata documentata). Strategia preferenziale per Linux: distribuire AppImage come primary (auto-update completo) e deb come secondary (manual update).

3. **UI in renderer (comunicazione esito, US-025 AC3)**.
   - Il main process inoltra gli eventi updater al renderer via IPC (`webContents.send('updater:event', { type, payload })`).
   - Il renderer (SPA React, `packages/app/`) sottoscrive gli eventi via API esposta in `preload` e mostra:
     - Toast/banner "Aggiornamento disponibile (vX.Y.Z) — scarica e installa" con bottone conferma.
     - Indicatore di progresso del download.
     - Toast finale di esito ("Aggiornato a vX.Y.Z" / "Errore aggiornamento: <messaggio>").
   - L'UI sfrutta i componenti di [[design system solids]] (vincolo `raw/tech_stack.md`). Dettaglio componenti = TSK-057.
   - L'utente può sempre rifiutare il riavvio immediato; l'update è applicato al successivo avvio.

4. **Sicurezza / integrità**.
   - electron-updater verifica automaticamente **SHA-512** dei pacchetti scaricati contro l'hash nei metadata YAML — protezione contro tampering della distribuzione.
   - In presenza di code signing ([[ADR-007]]), il binario aggiornato è verificato anche dalla validazione di firma del sistema operativo (Gatekeeper macOS / Authenticode Windows). Senza firma, la sola verifica SHA-512 resta attiva (sufficiente per integrità, non per autenticazione del publisher).
   - I metadata YAML sono serviti da GitHub via HTTPS (TLS by default).

### Strategia di versioning

- Versione applicativa = versione semver nel `package.json` di `packages/desktop/` (allineata al tag `v*`).
- electron-updater confronta versione installata vs versione del tag latest in `latest*.yml` con confronto semver — major/minor/patch normali; nessuna logica custom necessaria.
- Pre-release (tag con suffisso, es. `v1.0.0-beta.1`) supportati nativamente: `autoUpdater.allowPrerelease = false` di default (solo stable channels), opzionale `true` per canale beta futuro (fuori scope MVP).

### Configurazione di sviluppo

- In dev (`npm run dev:desktop`) l'auto-update è disabilitato (`autoUpdater.isUpdaterActive()` ritorna false in `app.isPackaged === false`).
- Per testare il flusso in locale prima del release: `dev-app-update.yml` con provider `generic` puntato a un file server locale (procedura standard electron-updater, di dettaglio in TSK-057).

## Conseguenze

### Positive

- **Coerenza ADR-007**: stessa famiglia di tool, stesso publisher, zero attrito di integrazione (metadata YAML generati e consumati nativamente).
- **Zero infrastruttura da gestire**: GitHub Releases è già il publish target — nessun server custom, nessun S3, nessun servizio terzo da mantenere/pagare.
- **Trigger di release allineato**: tag `v*` rilascia contemporaneamente web (Vercel, gap `vercel-deploy-trigger-policy` chiuso) e desktop (GitHub Releases) — un'unica operazione owner.
- **Integrità built-in**: SHA-512 + (quando firmato) validazione OS = doppia barriera contro pacchetti corrotti/maliziosi.
- **Tre AC US-025 coperti**:
  - AC1 (rileva nuova versione) → evento `update-available`.
  - AC2 (applicabile senza reinstallazione manuale) → `quitAndInstall` su Win/macOS/AppImage. Limite documentato su Linux deb.
  - AC3 (esito comunicato) → eventi `update-downloaded` / `error` → IPC → UI renderer.
- **Cross-platform**: un solo client per Win/macOS/Linux (con caveat deb sopra).
- **Manutenzione condivisa**: electron-updater è mantenuto attivamente dal team electron-builder con uso massivo nell'ecosistema.

### Negative / rischi

- **Linux deb non auto-updatable**: limite intrinseco dei pacchetti deb (richiedono `apt`/privilegi root). Mitigazione: AppImage come format primary su Linux + notifica manual-update su deb. Documentato per l'utente.
- **Repo pubblico assunto**: GitHub Releases provider `github` di electron-updater funziona idealmente con repo pubblici (nessun token richiesto al client). Se il repo dovesse passare a privato, sarebbe necessario un token utente o un provider alternativo (es. `generic` + S3). Per soli-boy il repo è già pubblico (`soli92/soli-boy`), quindi nessun problema corrente — annotato come assunzione esplicita.
- **Bandwidth GitHub**: GitHub Releases non ha limiti di download stringenti per repo pubblici, ma in caso di adozione massiva si potrebbe valutare un mirror CDN. Rischio molto basso per il volume previsto.
- **Differimento aggiornamenti macOS senza firma**: senza Developer ID + notarization, macOS Gatekeeper può bloccare l'avvio del binario aggiornato. Mitigazione: firma macOS come prerequisito human ([[ADR-007]]).
- **No rollback automatico**: electron-updater non offre rollback. Mitigazione: validare con beta channel prima dei release stable (fuori scope MVP, follow-up).

### Invariante

- I dati utente (ROM/save/SRAM/config) sotto `app.getPath('userData')` NON sono toccati dall'aggiornamento; solo il bundle applicativo viene sostituito ([[ADR-002]] privacy on-device).
- Nessun telemetry o tracking aggiunto: il check di update è una sola richiesta HTTPS verso GitHub Releases per i metadata, senza identificativi utente (vincolo US-033 / privacy).

## Alternative considerate

### `@electron/update-electron-app` + `update.electronjs.org` (Squirrel) (scartata)

Wrapper ufficiale Electron sopra Squirrel (Windows/macOS), backend hosted gratuito (`update.electronjs.org`).

- **Pro**: setup minimo (`require('update-electron-app')()`), backend gestito dal team Electron.
- **Contro**:
  1. Linux **non supportato** (Squirrel è solo Windows/macOS) → serve un secondo meccanismo per AppImage = duplicazione.
  2. Backend `update.electronjs.org` punta automaticamente ai GitHub Releases, ma è un servizio gestito da terzi senza SLA formale per progetti privati.
  3. Squirrel.Windows ha quirk noti (gestione startup, shortcut) e una community più piccola rispetto a NSIS + electron-updater.
  4. Richiede di aver scelto Electron Forge (o Squirrel diretto) per il packaging — incompatibile con la scelta di [[ADR-007]] (electron-builder + NSIS).

Sub-ottimale per un progetto che richiede copertura Linux completa.

### Squirrel diretto (Win+macOS) + meccanismo custom per Linux (scartata)

- **Pro**: massimo controllo.
- **Contro**: due meccanismi distinti da mantenere (Squirrel + custom Linux); fragilità; nessun beneficio rispetto a electron-updater che già copre i tre target.

### Server di update custom (scartata)

Hostare un endpoint REST proprietario che fornisca i metadata di update.

- **Pro**: controllo totale del rollout (es. staged rollout per geografia / percentuale).
- **Contro**:
  1. Infrastruttura da gestire (server, DNS, monitoring, costi).
  2. Over-engineering per un MVP single-publisher senza requisiti di staged rollout.
  3. Violazione del principio "soluzione proporzionata alla complessità".

Considerata e scartata in favore di GitHub Releases (zero ops, requisiti coperti).

### Tauri updater / altri (fuori scope)

Vincolato dalla scelta di Electron in `raw/tech_stack.md` e [[ADR-007]]. Non valutato.

## Pending / follow-up

- **TSK-057** (aggiornamento automatico, EP-006): implementazione del flusso, UI in-app (toast/banner), gestione preferenze utente (es. opt-out check automatico, scelta canale stable/beta in v2).
- **Code signing** (prerequisito human, R.14): senza firma, macOS può bloccare l'update; vedi [[ADR-007]].
- **Linux deb fallback UX**: definire copy del messaggio "manual update available" — di dettaglio in TSK-057.
- **Canali release** (stable / beta): fuori scope MVP, valutabile in v2 quando ci sarà una user base.
- **Telemetria adoption update**: NON inclusa (privacy on-device); se in futuro si vuole misurare il tasso di adozione, richiede ADR dedicato per consenso utente.
