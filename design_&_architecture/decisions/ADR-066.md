# ADR-066 — Confine functional-oracle ↔ interaction test, con runtime condiviso

## Contesto

EP-005 US-020 ha già un «interaction test» (oracolo strutturato binario, Leva 2): Playwright guida
un'interazione su un componente/pagina e verifica un esito. EP-018 introduce un oracolo funzionale
che pure guida interazioni Playwright. Rischio: due implementazioni parallele del «drive interaction»
→ drift, doppio punto di bug, viola il principio single-source già affermato per la cattura
(ADR-017, `screenshot-capture-protocol`).

## Decisione

**Capability distinte per scopo e trigger; runtime di interazione condiviso via skill interna.**

### A. Distinzione di scopo (non si fondono)

| | EP-005 US-020 interaction test | EP-018 functional oracle |
|---|---|---|
| **Scopo** | «questo componente/pagina reagisce all'interazione» | «l'app fa il suo lavoro core, end-to-end» |
| **Scala** | per-TSK, component/page | app-level, flusso cross-componente |
| **Trigger** | sub-step di Develop FE (Leva 2, dentro il loop visual oracle) | gate separato / standalone / candidato release gate (EP-012) |
| **Contratto** | `interaction_test_spec:` (file Playwright per-TSK) | `acceptance-spec` dichiarativo (ADR-065) |
| **Verdict** | binario per il loop del TSK | pass/conditional/reject app-level (ADR-065 §D) |

Sono **complementari**: l'interaction test è una verifica locale durante lo sviluppo; il functional
oracle è l'accettazione del flusso. Mantenerle separate evita di gonfiare il loop per-TSK con
scenari end-to-end e viceversa.

### B. Runtime condiviso: nuova skill interna `interaction-drive-protocol`

Si estrae il «drive interaction» Playwright in una **skill interna condivisa**
`interaction-drive-protocol` — single source of truth per l'esecuzione di passi di interazione
scriptati (click/type/set_input_files/wait_for/keyboard), analoga a `screenshot-capture-protocol`
(ADR-017) per la cattura. Vocabolario di azioni unico (`scenario[]` di ADR-065 = stesso vocabolario
usabile da `interaction_test_spec`).

Consumatori:
- `functional-oracle-protocol` (EP-018) → compone scenari app-level.
- `visual-oracle-protocol` / US-020 (EP-005) → può migrare l'interaction step su questa skill
  (refactor non distruttivo, opzionale, come fece ADR-017 per la cattura).

Niente MCP: Bash + Playwright (ADR-008), runner in `.factory-runners/` (gitignored), fail-loud su
prerequisito mancante, CWD del package target (ADR-064 §D).

### C. Nessuna nuova infrastruttura duplicata

`functional-oracle-protocol` **riusa**: `interaction-drive-protocol` (azioni), `screenshot-capture-protocol`
(evidenza/trace), app-lifecycle serve (ADR-064 Step 1.0), side-channel `code_quality/reports/`
(ADR-012). Aggiunge solo l'**asserzione** (ADR-065 §C) e la **composizione del verdict** (§D).

## Rationale

1. **Single-source per riga di runtime, capability distinte per semantica** — lo stesso pattern di
   ADR-017 (cattura condivisa, consumer diversi). DRY al livello dell'operazione, non della feature.
2. **Scopo ≠ scala**: fondere per-TSK e app-level produrrebbe loop o gate mal dimensionati. La
   separazione tiene il loop di Develop leggero e l'accettazione esplicita.
3. **Migrazione opzionale e non distruttiva** di US-020 sul runtime condiviso: nessuna regressione
   forzata su EP-005 (già done).

## Conseguenze

- **Positive**: zero duplicazione del runtime; vocabolario di interazione unico; EP-005 può
  beneficiare del refactor senza esservi obbligata.
- **Costi**: una skill interna in più (`interaction-drive-protocol`) da introdurre in Develop (US-018a
  ne dipende). Onere di coordinamento col team EP-005 per l'eventuale migrazione di US-020.
- **Scheduler**: nuovo dominio `functional-oracle` (serial same-app, parallel cross-app), distinto da
  `visual-oracle` (ADR-012 §F). Ordering nel cascade: `develop → visual-oracle → functional-oracle → review`.
