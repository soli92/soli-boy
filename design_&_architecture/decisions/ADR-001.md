# ADR-001 — Architettura a tre livelli con codebase condivisa

## Contesto

Il prodotto deve essere eseguito come SPA web, applicazione desktop e (in roadmap) app mobile, offrendo la stessa esperienza di emulazione su tutti i target. [^src: management/kanban/EP-003-esecuzione-e-controlli/US-010-avvio-emulazione/US-010.md §Descrizione]

I file di gioco e i salvataggi devono restare sul dispositivo, con caricamento sia nel browser sia, in modalità nativa, dal filesystem. [^src: management/kanban/EP-001-gestione-file-di-gioco/US-004-persistenza-libreria/US-004.md §Business Rules]

## Decisione

Si adotta un'unica applicazione (SPA) organizzata in tre livelli logici, confezionata per ciascun target tramite contenitori distinti:

- **Presentazione** — React + design system solids (componenti, token, temi).
- **Dominio/Servizi** — TypeScript: riconoscimento piattaforma, gestione sessione di gioco, mapping comandi.
- **Emulazione** — EmulatorJS (core Libretro WASM) per esecuzione e rendering audio/video.
- **Persistenza** — dietro un'astrazione (vedi [[ADR-002]]), implementata su IndexedDB nel browser/WebView.

Contenitori di confezionamento (logica e UI condivise, cambia solo il contenitore):

| Target | Contenitore |
|---|---|
| Web | SPA servita staticamente |
| Desktop | Electron (filesystem nativo, core offline) |
| Mobile | Capacitor (WebView + plugin nativi) |

## Conseguenze

- **Positive**: massimo riuso del codice e del design system; coerenza cross-platform; velocità di sviluppo (obiettivo primario).
- **Negative/rischi**: vincolo iOS su WebAssembly/JIT da validare (vedi [[ADR-003]] e US-035); per i core WASM con threading servono header COOP/COEP sul web.
- **Alternativa scartata**: React Native (riscrittura UI) — perde il riuso diretto dei componenti web solids e allunga i tempi.
