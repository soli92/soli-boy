# ADR-004 — Integrazione EmulatorJS reale

## Contesto

Il sistema deve avviare ed eseguire davvero il gioco con il core appropriato; finora l'app usa `StubEngine` (placeholder) e l'emulazione reale è un gap aperto (`emulatorjs-real-integration`). [^src: management/kanban/EP-003-esecuzione-e-controlli/US-010-avvio-emulazione/US-010.md §Acceptance Criteria]

Vincolo di stack: l'emulazione è delegata a EmulatorJS (core Libretro in WASM), senza core proprietari (`raw/tech_stack.md`). [^src: management/kanban/EP-003-esecuzione-e-controlli/US-010-avvio-emulazione/US-010.md §Business Rules]

Attrito tecnico: EmulatorJS è una **libreria a script globale** (non ESM) che si auto-monta in un elemento DOM, gestisce da sé loop/input/audio e si avvia al caricamento del gioco. Non mappa 1:1 sull'interfaccia `EmulatorEngine` (load→start, sendInput, …) definita in [[ADR-003]].

## Decisione

Si introduce un adapter **`EmulatorJsEngine implements EmulatorEngine`** (in `src/core/`) che incapsula EmulatorJS dietro l'interfaccia stabile esistente:

1. **Loading lazy**: il loader EmulatorJS è iniettato via `<script>` solo al primo avvio di un gioco (non nel bundle). Le globali `EJS_*` sono configurate prima dell'iniezione: `EJS_player` (container), `EJS_core` (dal `Core` risolto), `EJS_gameUrl` (Object URL del blob ROM), `EJS_pathtodata` (vedi hosting), `EJS_startOnLoaded`.
2. **Mount DOM**: il `Player` fornisce un container all'engine — estensione minima dell'interfaccia (`LoadOptions.container?: HTMLElement` o metodo `mount(el)`); lo `StubEngine` la ignora.
3. **Lifecycle → API EJS** (`EJS_emulator`): `start`=play, `pause`/`resume`=pause/resume del loop, `stop`=teardown + revoke dell'Object URL, `setAudio`=volume/mute, `setSpeed`=fast-forward (rewind via capability per-core).
4. **Hosting core (CDN web + self-host desktop/mobile)**: in web `EJS_pathtodata` punta al CDN EmulatorJS; in Electron/Capacitor i core sono vendati localmente per il funzionamento offline (RF-24). Vedi runbook [[emulatorjs-hosting]]. Per i core WASM con threading servono header COOP/COEP sul server web.
5. **Input (nativo EJS + InputMapping per touch)**: tastiera e gamepad sono gestiti nativamente da EmulatorJS; `InputMapping`/`sendInput` resta per i **controlli touch** (mobile), che emettono input sintetici verso il core. Si evita la doppia gestione: il wiring globale keydown a livello App va disattivato quando `EmulatorJsEngine` è attivo.
6. **Testing**: `EmulatorJsEngine` non è unit-testabile in jsdom (richiede WASM/DOM reali); `StubEngine` resta per unit + e2e deterministici. La validazione reale avviene con un **e2e dedicato + ROM homebrew libera** (chiude il gap `emulatorjs-real-integration`).

## Conseguenze

- **Positive**: emulazione reale senza cambiare il dominio (l'interfaccia `EmulatorEngine` regge); selezione engine a livello App (stub ↔ reale); offline garantito su desktop/mobile.
- **Negative/rischi**: dipendenza da una lib a script globale (loading/teardown da gestire con cura, revoke Object URL); doppio modello di input da tenere separato (nativo vs touch); COOP/COEP necessari per i core threaded; su iOS limiti WASM/JIT (vedi US-035, [[emulazione-su-mobile]]).
- **Vincolo legale**: l'adapter esegue solo file forniti dall'utente; nessun core/ROM protetto incluso (le ROM di test e2e sono homebrew libere).

## Pending / follow-up

- L'integrazione introduce nuovi TSK (adapter, mount nel Player, hosting, e2e con ROM) — taskizzazione a cura del TPM.
- iOS WASM/JIT: validazione in EP-008 (US-035), fuori da questo ADR.
