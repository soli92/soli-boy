1. Scopo dell'integrazione
Il presente documento integra le Specifiche Funzionali di Soli-boy (v1.0) estendendo l'ambito del prodotto alle piattaforme mobile. Oltre alle versioni web e desktop già previste, il prodotto dovrà essere disponibile come applicazione mobile nativa su Android e iOS.
L'obiettivo è offrire la medesima esperienza di emulazione — caricamento delle proprie ROM, libreria, esecuzione, salvataggi — adattata ai dispositivi touch, mantenendo coerenza funzionale e visiva con le altre versioni grazie al design system solids.
Nota terminologica: la richiesta originaria citava “Android e macOS”. Poiché macOS è un sistema desktop, in questo documento le piattaforme mobile sono intese come Android e iOS (il sistema mobile di Apple). Un eventuale target desktop macOS rientra nella distribuzione desktop Electron già descritta nelle specifiche di base.

3. Approccio tecnologico
Per massimizzare il riuso della codebase esistente (React + TypeScript + solids) ed essere coerenti con l'obiettivo di velocità di sviluppo, si valutano due strategie principali per il confezionamento mobile.
3.1 Opzione A — Capacitor (consigliata)
Capacitor incapsula la SPA web esistente in un contenitore nativo per Android e iOS, esponendo le API native (filesystem, gamepad, haptics) tramite plugin. È la via più rapida perché riutilizza quasi integralmente il codice React e i componenti solids già sviluppati.
	•	Riuso massimo della codebase web e del design system.
	•	Accesso al filesystem nativo per ROM, BIOS e salvataggi tramite plugin.
	•	Un'unica logica applicativa condivisa tra web, desktop (Electron) e mobile (Capacitor).
3.2 Opzione B — React Native
Una riscrittura dell'interfaccia in React Native offrirebbe maggiore integrazione nativa, ma comporterebbe la perdita del riuso diretto dei componenti web solids e tempi più lunghi. È sconsigliata in prima battuta data la priorità sulla velocità.
3.3 Emulazione su mobile
I core EmulatorJS (WASM) restano il motore di emulazione anche su mobile, eseguiti all'interno del WebView del contenitore Capacitor. Vanno verificate le prestazioni su dispositivi di fascia media e l'inclusione locale dei core per il funzionamento offline.
Vincolo iOS: su iOS l'esecuzione di WebAssembly avviene tramite il motore WebView di sistema; vanno verificati i limiti di JIT e prestazioni. Le politiche dell'App Store sugli emulatori sono cambiate di recente e vanno validate in fase di pubblicazione, assicurandosi che l'app non distribuisca contenuti protetti.

6. Impatti sull'architettura
L'aggiunta delle versioni mobile estende il modello di distribuzione condiviso. La logica applicativa, l'interfaccia React e i componenti solids restano condivisi; cambiano i contenitori di confezionamento per ciascun target.

Capacitor

Componenti condivisi tra tutti i target:
	•	Interfaccia utente React e design system solids.
	•	Servizi di dominio (riconoscimento piattaforma, gestione sessione, mapping comandi).
	•	Motore di emulazione EmulatorJS/WASM.
	•	Logica di persistenza (astratta su un'interfaccia di storage adattata a IndexedDB/web e filesystem/nativo).
